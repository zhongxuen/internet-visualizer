# API authentication

Two questions, constantly confused, and HTTP has a different status code for each:

- **Authentication** — who is calling? A failure here is `401 Unauthorized`, and the
  response owes the client a `WWW-Authenticate` field naming the scheme to use.
- **Authorisation** — may this caller do this? A failure here is `403 Forbidden`, and
  there is nothing the client can change about its credentials to fix it.

`401` means _I do not know you_. `403` means _I know exactly who you are, and no_.

## Keys, tokens, and where they must not go

An API key is a long random string that identifies a caller and usually nothing else. A

<Term id="bearer-token">bearer token</Term> is the same idea with structure: it says who
you are, what you may do, and when it stops being true.

"Bearer" is the whole security model — possession is sufficient. That has two immediate
consequences:

```text
Authorization: Bearer eyJhbGciOi...     good: a header, over TLS, not logged by default
GET /v1/orders?api_key=sk_live_9f3...   bad:  now in access logs, browser history,
                                              Referer headers, and every screenshot
```

A JWT is worth understanding concretely: the payload is base64url, which is an encoding
and not encryption. Anyone holding the token can read every claim in it. The signature
makes it tamper-**evident**, not confidential — and a verifier must decide which
algorithms it accepts before it reads the token, or it will be told.

## Acting on somebody else's behalf

The harder problem is an application that needs to use _your_ account somewhere else.
Handing it your password gives it everything, forever, with no way to take it back.

<Term>OAuth</Term> is the answer, and the shape of it is worth holding in your head:

<EmbeddedSim module="api-visualizer" scenario="oauth-authcode-pkce" />

You type your password into the authorization server and nowhere else. It hands the
application a short-lived code _through the browser_; the application exchanges that code
for a token over a direct back-channel, so the token itself never travels through the
browser at all.

PKCE closes the remaining hole. The client commits to a secret before the user even
authenticates, and must produce it at the exchange — so a stolen code is worthless to
whoever stole it.
