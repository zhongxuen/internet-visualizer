# Keeping a WebSocket alive

An open socket is not a working one. TCP will happily let a program write to a peer that
vanished minutes ago, and nothing reports the problem until something forces the issue.

Two things go wrong on a long-lived connection, and both are invisible:

- The peer disappears — crashed, rebooted, driven into a tunnel — and your end still
  believes the connection is fine.
- A middlebox on the path decides the flow is idle and drops its state. A
  <Term>NAT</Term> table or a <Term>load balancer</Term> commonly gives an idle connection
  30 to 60 seconds.

## Eight bytes, twice a minute

A ping frame costs eight bytes and buys both fixes at once: proof the peer is alive, and
enough traffic that nothing on the path considers the flow idle. The interval must beat
the shortest timeout anywhere on the path, which is why 25 seconds is a common choice.

Two details that surprise people:

- Answering a ping is an **obligation**, not a courtesy, and browsers do it automatically
  without telling the page. The pong must echo the ping's payload back byte for byte,
  which is what lets a sender match a pong to its ping and measure a round trip.
- Browsers cannot _send_ pings. The WebSocket API has no method for it. The heartbeat is
  therefore the server's job in any browser-facing deployment.

## Closing properly, and the code that is never sent

A clean close is a handshake: one Close frame out, one echoed back, and only then does
TCP come down. `wasClean` is true only when both crossed — which is the one reliable way
to distinguish an intentional shutdown from a connection that simply died.

<EmbeddedSim module="websocket-viewer" scenario="close-handshake" />

Four close codes — 1004, 1005, 1006 and 1015 — can never appear in a frame at all. They
are what a local API reports when there is no frame to read a code from. `1006` in
particular means "no Close frame arrived", and it carries no reason because there was
nothing to carry one.

A reconnection is a genuinely new connection: new handshake, new key, and no memory of
the old one. Any messages sent during the gap are gone unless your application asks for
them back — which is the one thing <Term>SSE</Term> gets for free.
