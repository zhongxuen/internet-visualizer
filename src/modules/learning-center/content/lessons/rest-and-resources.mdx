# REST, and what GraphQL changes

An <Term>API</Term> is ordinary HTTP with the audience changed. Because the caller is
code rather than a person, the parts that matter most are the ones a human would forgive:
exact status codes, stable shapes, and errors that say what to do next.

<Term>REST</Term>'s organising rule is that the URL names a thing and the method is the
only verb.

```http
GET    /posts        list them
POST   /posts        create one; the server names it
GET    /posts/7      read that one
PUT    /posts/7      replace it entirely
PATCH  /posts/7      change part of it
DELETE /posts/7      remove it
```

Putting the verb in the method rather than the path is what lets every cache and proxy
between the client and the server reason about a request without understanding the
application at all.

## Idempotency is about the state, not the status

The run above sends POST and PUT twice each, because this is the property everything else
depends on. Two identical POSTs create two resources; two identical PUTs leave one. That
is why a client library may safely retry a PUT after a timeout and may not retry a POST.

DELETE answering 404 the second time is _still_ <Term>idempotent</Term>. Idempotency is a
claim about the state left behind, not about the response.

| Status | Says                              | Carries                          |
| ------ | --------------------------------- | -------------------------------- |
| 201    | A resource now exists             | `Location`, naming it            |
| 202    | Accepted, not done                | `Location`, pointing at progress |
| 204    | Done, and there is nothing to say | No body at all — not even `{}`   |
| 405    | Wrong method for a real resource  | `Allow`, listing what works      |
| 422    | The JSON parsed and made no sense | An explanation                   |

## What GraphQL trades away

<Term>GraphQL</Term> takes the opposite position: one endpoint, one POST, and the client
describes the shape of the response it wants. A screen needing a user, their posts, and
each post's comment count is one request instead of several, and returns no field the
client did not ask for.

<EmbeddedSim module="api-visualizer" scenario="rest-vs-graphql" />

What is given up is everything that came from having a method and a URL. HTTP caching
does not apply to a POST to one endpoint. Per-resource authorisation has to be
reimplemented inside the resolver layer. And the cost of a request is no longer obvious
before it runs, because the client wrote the query.
