# The upgrade, and the frames after it

A <Term>WebSocket</Term> does not start as a WebSocket. It starts as an ordinary
HTTP/1.1 GET on port 443, with a few fields that ask the server to stop speaking HTTP.

```http
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=

```

That blank line after the `101` is the same framing device from track 4, doing its last
job: it is the exact byte at which HTTP ends and frames begin.

## Why it looks like HTTP at all

Because that is what deploys. A WebSocket connection traverses corporate proxies, load
balancers and firewalls that have never heard of WebSockets, precisely because the first
thing they see is a GET to port 443 with a Host field.

`Sec-WebSocket-Accept` is the server hashing the client's key together with a fixed,
published GUID. It is not a secret and proves nothing about identity — it is a proof of
_comprehension_, showing that whatever answered actually understood the request rather
than a cache replaying an old `101`.

## Frames, and the message that spans several

After the `101` there is no request/response pairing at all — just two independent
streams of <Term>frame</Term>s sharing one socket. A frame is a couple of bytes of
header and then payload, which is why a chat message costs about eleven bytes total.

A message is not a frame. A sender that does not yet know how long its message will be
can start sending anyway: the first frame carries the type with FIN clear, every frame
after it carries the continuation opcode, and the last one sets FIN.

The length field has three encodings — 0–125 inline, then 126 meaning "the real length is
in the next two bytes" and 127 meaning "the next eight" — and the encoding must be
minimal, because two legal spellings of one frame is how parsers come to disagree.
